# 实机仿真复现流程

## 1.作者github仓库提供的实际部署流程

~~~
# In every terminal
source ros_ws/devel/setup.bash

# T1 MAVROS
sudo chmod 666 /dev/ttyACM0
roslaunch mavros px4.launch fcu_url:=/dev/ttyACM0:57600

# After MAVROS connects: IMU / attitude at 200Hz
rosrun mavros mavcmd long 511 105 5000 0 0 0 0 0  # HIGHRES_IMU
rosrun mavros mavcmd long 511 31  5000 0 0 0 0 0  # ATTITUDE_QUATERNION
rosrun mavros mavcmd long 511 83  5000 0 0 0 0 0  # ATTITUDE_TARGET

# T2 MID360 + FAST-LIO + EKF
roslaunch fast_lio fastlio_ekf.launch

# T3 px4ctrl
roslaunch px4ctrl run_ctrl.launch

# T4 M-detector
roslaunch m_detector detector_mid360.launch

# T5 OmniRisk
source omnirisk_env/bin/activate
cd OmniRisk && python omnirisk_node.py --use_tensorrt 1

# T6 RViz
rviz -d OmniRisk/omnirisk.rviz

# T7 Joystick goal (_input_mode:=usb | mavros)
cd OmniRisk && python3 rc_goal_teleop.py _input_mode:=usb

# Takeoff / land
rostopic pub -1 /px4ctrl/takeoff_land quadrotor_msgs/TakeoffLand "takeoff_land_cmd: 1"
rostopic pub -1 /px4ctrl/takeoff_land quadrotor_msgs/TakeoffLand "takeoff_land_cmd: 2"

# Checks
rostopic hz /ekf_quat/ekf_odom              # > 50Hz
rostopic hz /mavros/setpoint_raw/attitude   # > 100Hz
rostopic hz /so3_control/pos_cmd
~~~



## 2.模块之间的通信

各个模块之间通过ROS话题通信

| 模块                       | 建议运行位置   | 作用                                     |
| -------------------------- | -------------- | ---------------------------------------- |
| T1 MAVROS                  | 机载电脑       | 通过 USB/串口连接 PX4 飞控               |
| T2 MID360 + FAST-LIO + EKF | 机载电脑       | 接收雷达数据，估计无人机位置、速度和姿态 |
| T3 px4ctrl                 | 机载电脑       | 将规划指令转换为飞控接收的姿态、推力指令 |
| T4 M-detector              | 机载电脑       | 检测和跟踪动态障碍物                     |
| T5 OmniRisk                | 机载电脑       | 加载模型，实时规划避障轨迹               |
| T6 RViz                    | 通常放地面电脑 | 显示点云、轨迹、状态                     |
| T7 Joystick goal           | 取决于输入来源 | 将摇杆操作转换为导航目标                 |



整体的数据流向为：

MID360 + FAST-LIO + EKF提供的周围静态障碍物点云信息以及无人机自身的位置速度姿态信息——>

M-detector根据点云信息检测并跟踪动态障碍物——>

Omnirisk接收depth+mask+velocity+obs四个张量输入神经网络，输出运动轨迹——>

px4ctrl根据期望轨迹、当前位姿、IMU 等信息计算期望姿态和推力，实现轨迹跟踪控制——>

MAVROS将轨迹跟踪信息转换为MAVLink信息，通过串口发送给PX4飞控执行。

## 3.各个模块的输入输出

### MID360雷达：测量环境并输出ROS数据

roslaunch fast_lio fastlio_ekf.launch中，会一起启动雷达驱动、FAT-LIO以及EKF



输入（或者也可以认为不需要输入）：

- MID360 通过网络发送的雷达测量数据。
- 雷达内置 IMU 的加速度计、陀螺仪数据。



输出：

| 话题topic      | 内容                                 |
| -------------- | ------------------------------------ |
| `/livox/lidar` | 雷达点云，FAST-LIO 接收的 Livox 数据 |
| `/livox/imu`   | 雷达自身 IMU 的测量                  |



该模块主要负责**负责采集和发布数据**



###  **FAST-LIO**：**通过雷达和 IMU 估计飞机运动**

要处理的问题：飞机相对于启动时建立的参考坐标系，移动了多少、转动了多少？



输入：

| 输入                    | 来源                                   |
| ----------------------- | -------------------------------------- |
| 雷达点云 `/livox/lidar` | 雷达驱动                               |
| IMU `/livox/imu`        | 雷达内置 IMU                           |
| 雷达与 IMU 的外参       | 配置文件，描述两者的相对安装位置和方向 |



输出：**输出：**

| 话题                                | 内容                     |
| ----------------------------------- | ------------------------ |
| `/Odometry`                         | 估计的位置、姿态、速度等 |
| `/cloud_registered_no_point_filter` | 转到世界坐标系的当前点云 |



核心过程：

**第一步：用 IMU 预测运动。**

​		 由上一时刻的位置、速度和姿态，利用角速度、加速度预测下一时刻状态。但 IMU 有噪声和偏置，积分时间越长，位置误差越容易累积。

**第二步：补偿扫描期间的运动畸变。**

​        一帧雷达数据中的点不是完全同时采集的。如果飞机在扫描期间移动，直接把所有点当作同一时刻的测量，会把墙面等结构“拉歪”。

FAST-LIO 利用 IMU 预测的运动，将这些点补偿到统一参考时刻。

**第三步：把当前扫描与已有局部地图匹配。**

​        根据已有局部地图，结合当前雷达扫描结果，修正飞机位姿

**第四步：迭代更新状态并维护地图**

​        通过迭代误差状态滤波，将 IMU 预测和雷达几何约束结合，更新位置、姿态、速度、偏置等状态，再把合适的点加入地图。

相关实现见 laserMapping.cpp (ros_ws/src/FAST_LIO/src/laserMapping.cpp:797)。

这里建立的“世界坐标系”通常是启动时定义的局部参考系，不必是 GPS 全球坐标系



### **EKF：将 FAST-LIO 状态与飞控 IMU 融合，提供高频状态**

**FAST-LIO 已经融合过雷达自己的 IMU，而这个额外 EKF 接入的是飞控通过 MAVROS 发来的 IMU**

主要作用：在雷达定位更新之间，持续提供适合控制使用的高频状态。



**输入：**

| 话题               | 内容                |
| ------------------ | ------------------- |
| `/Odometry`        | FAST-LIO 的位姿估计 |
| `/mavros/imu/data` | 飞控 IMU 数据       |



**输出：**

```
/ekf_quat/ekf_odom，
消息类型为 nav_msgs/Odometry，包含位置、姿态、速度等。发布频率与有效 IMU 输入及运行情况有关，不能仅凭配置保证一定达到 200 Hz。
```



当前实现维护的状态可以写成：

x=[p,q,v,b_{g},bₐ]

分别是位置、四元数姿态、速度、陀螺仪偏置和加速度计偏置。



**原理分为预测和校正：**

- 每来一条飞控 IMU，预测状态如何变化。
- FAST-LIO 位姿到达后，计算它与预测状态之间的误差。
- 根据状态和测量的不确定性，计算卡尔曼增益，修正状态。

由于 FAST-LIO 结果可能存在处理延迟，代码还保存历史状态和 IMU，用于在相应时间修正后，再向当前时刻重新传播。

因此，它不是把同一个低频位置复制很多次，而是在两次定位更新之间，利用真实 IMU 测量推进运动状态。

输入输出配置见 ekf_quat_lidar_mavros.launch (ros_ws/src/ekf_quat_pose/launch/ekf_quat_lidar_mavros.launch:3)。



###  **M-detector：判断哪些点属于运动物体，并跟踪它们**

FAST-LIO 回答“我在哪里”，M-detector 回答：环境中哪些东西正在动？它们在哪里，往哪里运动



输入是：

| 话题                                | 内容                           |
| ----------------------------------- | ------------------------------ |
| `/cloud_registered_no_point_filter` | 世界坐标系中的当前点云         |
| `/Odometry`                         | 与点云配合使用的 FAST-LIO 位姿 |

注意，当前默认检测器使用 `/Odometry`，规划器和控制器主要使用 `/ekf_quat/ekf_odom`，两者并不完全相同。



**主要输出：**

| 话题                                             | 内容                                   |
| ------------------------------------------------ | -------------------------------------- |
| `/m_detector/std_points`                         | 被判定为静态的点云                     |
| `/m_detector/confirmed_tracks`                   | 已确认动态目标的位置、速度、尺寸和 ID  |
| `/m_detector/point_out`、`/m_detector/frame_out` | 动态点相关输出，供跟踪、显示或调试使用 |



该模块分为动态障碍物检测和目标跟踪两部分

**① 动态点检测：比较多帧几何关系。**

仅比较两个点的坐标变化不够，因为无人机自己也在动。

系统需要利用位姿，将不同时间的测量放到可比较的参考关系中，再结合历史深度图检查：

- 当前点与静态环境是否一致。
- 同一方向的深度变化能否由遮挡解释。
- 多个时刻的观测是否支持该点属于运动物体。

例如，飞机移动时，墙在雷达局部坐标系中的位置会变；但经过正确的自身运动补偿，墙应保持在固定世界位置。飞来的球则仍会表现出独立运动。

**② 聚类：把动态点组成目标。**

一颗球可能产生多个雷达点。系统按空间邻近关系将其聚成点簇，计算中心、尺寸和包围盒。

**③ 数据关联：判断这一帧的球是不是上一帧那颗球。**

跟踪器先预测已有目标的位置，再比较当前检测与预测是否匹配。当前实现包含卡尔曼滤波、关联门限和匈牙利匹配等机制。

**④ 状态估计和生命周期管理。**

匹配后更新位置、速度；短暂漏检时做有限时间预测；缺乏足够观测或长期丢失的轨迹不再保留。

运动模型可配置为：

​						p(t+Δ t)=p(t)+v(t)Δ t

或加入已知重力的抛体模型：

​                       p(t+Δ t)=p(t)+v(t)Δ t+1/2gΔ t²                     

当前实机配置启用了抛体模型，适合投掷物；仿真匀速球配置会关闭它。

最终每个目标消息主要包含：

```
ID、是否确认、是否本帧匹配、年龄、命中次数、位置、速度、尺寸
```

实现见 DynObjFilter.cpp (ros_ws/src/M-detector/src/DynObjFilter.cpp) 和 FrameTracker.cpp (ros_ws/src/M-detector/src/FrameTracker.cpp)。



### **OmniRisk：将感知信息转换成可执行的避障轨迹**

使用已经训练好的网络进行轨迹预测



**输入：**

| 输入                                         | 用途                       |
| -------------------------------------------- | -------------------------- |
| 当前点云 `/cloud_registered_no_point_filter` | 表示当前可见环境           |
| 静态点云 `/m_detector/std_points`            | 提供静态环境信息           |
| 动态目标 `/m_detector/confirmed_tracks`      | 提供障碍物位置、速度和尺寸 |
| 状态 `/ekf_quat/ekf_odom`                    | 确定飞机当前运动状态       |
| 目标 `/move_base_simple/goal`                | 指定希望飞往的位置         |
| 模型权重或 TensorRT 引擎                     | 提供学习后的预测能力       |



**输出：**

```
/so3_control/pos_cmd
```

消息类型为 `quadrotor_msgs/PositionCommand`，主要包含期望位置、速度、加速度、jerk（加速度的变化率）、偏航角等。

它不是直接输出电机转速。



主要实现流程如下：

**① 对齐时间和坐标系。**

点云、动态目标和状态有各自时间戳，必须尽量表达同一时刻的场景。

例如，球每秒移动 4 米，错用 0.1 秒前的位置，就会产生约 0.4 米误差。当前代码包含缓存、同步、有限预测和过期结果丢弃机制。

**② 构造网络输入。**

三维点先转到以飞机为中心的规划参考系，再投影成球面距离图：

r=√(x²+y²+z²)

θ=atan2(y,x),  ϕ=atan2(z,√(x²+y²))

水平角和垂直角决定图像位置，距离决定像素值。

当前配置先构造约 `96×360` 的全景表示，再映射到网络使用的 `96×384`。

动态目标经过几何投影，形成：

- 障碍物掩码：哪些像素属于动态目标。
- 速度图：这些像素对应目标的三维速度。

另外构造 9 维状态：

```
当前速度3维 + 参考加速度3维 + 目标偏移3维
```

这里的参考加速度在运行时主要来自规划参考，并不是直接把 IMU 原始加速度塞进网络。

**③ 网络生成候选终点和评分。**

当前配置包含：

```
12个水平方向 × 3个垂直方向 = 36个候选
```

每个候选输出：

```
终点位置、终点速度、终点加速度
静态综合代价评分
动态风险评分
```

静态分支使用距离图和状态；动态分支额外使用掩码和速度图。

**④ 综合评分，选择候选。**

基本形式为：

Jᵢ=J_{static,i}+λ J_{dynamic,i}

然后选择代价较低的候选。当前代码还加入连续性代价和切换迟滞，避免相邻时刻频繁左右切换。

这些评分是模型预测的代价，不等于严格的碰撞概率。

**⑤ 用五次多项式构造连续轨迹。**

每个坐标轴使用：

p(t)=c₀+c₁t+c₂t²+c₃t³+c₄t⁴+c₅t⁵

利用起点和终点的：

```
位置、速度、加速度
```

共六个约束求出六个系数。

这样既能得到位置，也能通过求导得到速度、加速度和 jerk。当前控制参考定时器周期为 `0.02 s`，即名义上约 50 Hz；新的感知结果到来后会重新规划。

实现见 omnirisk_node.py (OmniRisk/omnirisk_node.py:1341)、network.py (OmniRisk/policy/network.py:47) 和 poly_solver.py (OmniRisk/policy/poly_solver.py:4)。

TensorRT 作用于这里的网络前向计算，周围的数据同步、投影、轨迹生成等仍由其他代码执行。









### **px4ctrl：把轨迹参考变成姿态和推力**



**输入：**

| 话题                    | 内容                     |
| ----------------------- | ------------------------ |
| `/so3_control/pos_cmd`  | OmniRisk 给出的期望运动  |
| `/ekf_quat/ekf_odom`    | 实际位置、速度和姿态     |
| `/mavros/imu/data`      | 飞控 IMU 和姿态信息      |
| `/mavros/state`         | 飞控连接、解锁、模式状态 |
| `/mavros/rc/in`         | 遥控输入                 |
| `/mavros/battery`       | 电池状态                 |
| `/px4ctrl/takeoff_land` | 起降请求                 |



**主要输出：**

```
/mavros/setpoint_raw/attitude
```

当前实际发送的是：

```
期望姿态四元数 q_d
归一化推力指令
```



具体控制包含以下步骤。

**① 比较期望与实际运动。**

当前代码使用串级位置、速度反馈。忽略限幅时，可近似写为：

v_{cmd}=v_{d}+Kₚ(p_{d}-p)

a_{cmd}=a_{d}+Kᵥ(v_{cmd}-v)

位置误差修正速度目标，速度误差再修正加速度目标。实际代码会限制误差和倾角等，避免过大的控制输出。

**② 将期望加速度转换成推力方向。**

忽略空气阻力时：

F_{d}=m(a_{cmd}-g)

四旋翼主要沿机体竖直轴产生总推力，所以要向右加速，就需要适当倾斜，使推力具有向右的分量。

结合期望偏航角，就能确定期望姿态；推力大小则与总力需求有关。

当前默认算法还利用轨迹 jerk 等信息计算前馈量，并进行飞控姿态参考系对齐。

**③ 将力需求转换为实际推力指令。**

发给 PX4 的 `thrust` 是归一化指令，并不是牛顿值，也不是简单的“电机油门百分比等于推力百分比”。

控制器需要使用推力模型，将加速度需求映射为指令，并可根据 IMU 反馈估计模型参数。

**④ 状态机管理。**

px4ctrl 还管理手动、悬停、轨迹跟踪、起飞和降落等状态，并通过 MAVROS 请求解锁、切换 Offboard 模式。

当前配置最大控制循环频率为 200 Hz，实际频率仍需要运行测量。

一个关键细节：虽然代码中也计算了角速度相关量，**当前发布函数将角速度设为忽略，实际采用姿态加推力接口**，见 PX4CtrlFSM.cpp (ros_ws/src/px4ctrl/src/PX4CtrlFSM.cpp:567)。位置速度反馈实现见 controller.cpp (ros_ws/src/px4ctrl/src/controller.cpp:690)。



### **MAVROS：连接 ROS 与 PX4 的通信桥梁**

主要解决：ROS 程序中的消息，怎样变成 PX4 能理解的通信数据？飞控数据怎样返回 ROS？



它有两个方向。

**机载电脑 → 飞控：**

| ROS 输入                        | 发给飞控的内容   |
| ------------------------------- | ---------------- |
| `/mavros/setpoint_raw/attitude` | 姿态和推力设定值 |
| `/mavros/set_mode` 服务         | 模式切换请求     |
| `/mavros/cmd/arming` 服务       | 解锁、上锁请求   |

MAVROS 将这些转换为 MAVLink 消息，通过 USB、UART 或其他配置好的链路发送。

**飞控 → 机载电脑：**

| ROS 输出           | 内容                 |
| ------------------ | -------------------- |
| `/mavros/imu/data` | IMU 测量和姿态       |
| `/mavros/state`    | 连接、解锁、飞行模式 |
| `/mavros/rc/in`    | 遥控通道             |
| `/mavros/battery`  | 电池数据             |

MAVROS 还处理接口约定下的坐标转换。ROS 常使用 ENU、FLU，而 PX4 常使用 NED、FRD，不能把两套坐标中的数值未经转换直接互用。

它本身不负责选择避障路线，也不负责本项目中的轨迹跟踪控制律。



### **PX4：执行姿态和角速度控制，分配电机输出**

PX4 运行在飞控硬件中。

**输入：**

- MAVROS 传来的期望姿态和推力。
- 飞控本地 IMU、姿态估计。
- 遥控、模式和其他飞行状态。

**输出：**

- 各电机的执行指令，通过 PWM、DShot 等接口发送给电调。
- 经 MAVLink 返回的状态和传感器消息。

在这套“姿态＋推力”接口下，可以理解成：

```
期望姿态与实际姿态的误差
    ↓
生成期望角速度
    ↓
期望角速度与陀螺仪角速度的误差
    ↓
计算所需力矩
    ↓
结合总推力，进行控制分配
    ↓
各个电机指令
```



## 4.Omniris算法原理解析

核心链路是：**离线学习轨迹风险 → 在线构建全景距离、动态掩码与速度图 → 双分支网络预测 36 个候选 → 融合评分选轨 → 五次多项式重建 → 控制执行。**



### 项目框架

论文原文提供：左侧仿真/实机共用输入，中部双分支网络，右上方训练期风险监督，右下方在线评分与轨迹生成。

### 网络输入：五通道全景图

**五通道输入的实现，本质上是：把不规则的雷达点云和动态跟踪结果，整理成五张空间对齐的全景图，再分两路送进网络。**

**通道形状：**

**每个单独通道都是一张 96×384 的二维图。** 距离占 1 个通道，掩码占 1 个通道，三维速度占 3 个通道，合计 5 个。这些尺寸由**角度网格划分和网络输出结构共同设计**，不会随点云数量或障碍物数量改变。

Iₜ=[Dₜ,Mₜ,Vₜ]∈ℝ^{H× W×5}，论文使用“高 × 宽 × 通道”的写法：

| 数据                                                 | 通道数 | 单帧形状 |
| ---------------------------------------------------- | -----: | -------- |
| 距离图 D：沿该网格对应方向到最近表面的距离，单位为米 |      1 | 96×384×1 |
| 动态掩码 M：0 或 1，表示该网格是否对应动态目标       |      1 | 96×384×1 |
| 速度分量 Vₓ                                          |      1 | 96×384×1 |
| 速度分量 V_{y}                                       |      1 | 96×384×1 |
| 速度分量 V_{z}                                       |      1 | 96×384×1 |
| 三维速度图 V：该表面对应目标的三维速度，单位为 m/s   |      3 | 96×384×3 |
| 概念上的完整输入 I=[D,M,V]                           |      5 | 96×384×5 |



#### 距离图构建：

**当前点云与静态背景点云 → 分别投影成距离图 → 对应格子取较近距离 → 合成可见动态目标球体的表面距离 → 补全缺失位置 → 映射为96×384并归一化 → 输入网络。**

首先，雷达扫描会得到一批三维数据点云，每个点用 (x,y,z) 表示测得的表面位置。这些点分布不规则，数量也会随场景和扫描情况变化，并不是天然排列好的图像。FAST-LIO 负责定位、运动补偿和点云注册，并将点云转换到世界坐标系。规划节点把点云、静态背景、动态目标及本机状态对齐到同一感知参考时刻，再转换到统一的局部规划坐标系。当前全向配置中，这个坐标系以无人机位置为原点，坐标轴方向与世界坐标系一致。

接着，为了将不规则点云整理成神经网络容易处理的输入，程序预先建立一张 **96 行、360 列的角度网格**。横向覆盖水平一圈，相邻列间隔 1°，对应360个采样方向；纵向覆盖 −7° 到 +52° 的俯仰范围，设置 96 个采样方向，相邻行间隔 约0.621°，每个网格对应一个观察方向。这里的96和360都是作者人为定义的，是否最佳工程选项有待商榷。

程序对每个三维点计算距离、方位角和俯仰角：
$$
r=√(x²+y²+z²),  θ=atan2(y,x),  ϕ=atan2(z,√(x²+y²))，
$$
再根据两个角度将它分配到最近的网格位置，把距离写入该格，具体分配规则见补充。

同一格落入多个点时，保留最近的距离。这样，数量不固定的点云就变成了尺寸固定的二维距离图。图中的行列表示方向，格子里的数值表示沿该方向测得的表面距离。

当前点云投影默认保留0.1米至20米之间、且位于指定俯仰范围内的有限点。图像初始值为20米，没有有效回波落入的格子暂时保留该值，供后续补全处理；这个值不能直接解释为已测得的表面距离或确定的自由空间。

距离图还会融合当前点云和静态背景信息。程序分别投影两类点云，在相同网格位置取较近的距离，形成基础距离图。

在基础距离图上，程序进一步利用动态目标的跟踪位置和尺寸构造球体近似模型，计算角度网格中各方向射线与球体表面的交点距离。多个目标覆盖同一方向时，保留最近的动态表面，再与基础距离图比较以判断遮挡。对于可见位置，保留基础距离与动态表面距离中的较近值，从而利用目标模型补充稀疏回波未覆盖的动态表面区域。



**1.世界坐标系如何确定？**

**FAST-LIO建立一个供整套系统共用的世界坐标系**，并且启动后保持不变

在当前 FAST-LIO 默认建图路径中：

- **原点**：将初始化时的 IMU 位置设为 (0,0,0)。
- **竖直方向**：利用初始化期间 IMU 的平均加速度估计重力方向，建立 z 轴向上、重力向下的坐标约定。
- **水平方向**：由初始化姿态约定确定。仅靠重力无法确定正北方向，因此这里的世界系 x 轴不能直接理解为东或北。

无人机运动后，FAST-LIO结合 IMU 和点云与地图的匹配，持续估计无人机在世界系中的位置与姿态。一个雷达测得的点转换到世界系，代码对应的关系为：
$$
p^{W} = R_{WB} (R_{BL}p^{L}+t_{BL}) +t_{WB}.
$$
这里：

| 符号          | 含义                                |
| ------------- | ----------------------------------- |
| p^{L}         | 雷达测得的点坐标                    |
| R_{BL},t_{BL} | 雷达到 IMU 的安装旋转与平移，即外参 |
| R_{WB},t_{WB} | IMU在世界系中的姿态与位置           |
| p^{W}         | 转换后的世界坐标                    |



**2.局部规划坐标系如何建立？**

当前全向模式采用的规则非常直接：

> **每一帧以感知参考时刻的无人机位置为原点，三个坐标轴与世界系保持同向。**

因此，世界系中的点转换到局部规划系，只需做减法：
$$
p^{Pₜ} = p^{W}-pᵤₐᵥ^{W}(t)
$$
例如：

| 对象     | 世界坐标 |
| -------- | -------- |
| 无人机   | (10,3,1) |
| 墙上的点 | (14,5,2) |

墙上这个点在当前局部规划系中的坐标为：
$$
(14,5,2)-(10,3,1)=(4,2,1).
$$
它表示：从无人机出发，沿世界 +x 方向4米、+y 方向2米、+z 方向1米。

下一帧无人机移动到 (11,3,1)，同一个静态点就变成：
$$
(14,5,2)-(11,3,1)=(3,2,1).
$$
**点在世界系中的位置没有变化，但相对于无人机的位置发生了变化。**

还要区分局部规划系与机体系：

| 坐标系            | 原点             | 轴向是否随机身旋转 |
| ----------------- | ---------------- | ------------------ |
| 世界系 W          | 初始化时确定     | 不随               |
| 当前局部规划系 Pₜ | 当前帧无人机位置 | 不随，保持世界轴向 |
| 机体系 B          | 机体参考点       | 随机身旋转         |

在当前全向配置中，**无人机原地转头不会让规划坐标轴跟着转动**



**3.当前点云与静态背景如何融合？**

当前默认的当前点云话题是 `/cloud_registered_no_point_filter`，静态背景话题是 `/m_detector/std_points`。这两类点云进入规划节点时都已经使用世界坐标。**M-detector先累积近期静态背景点云，规划节点再将它与当前点云分别投影，逐格保留较近的距离**

**第一步：M-detector建立近期静态背景。**

FAST-LIO每完成一帧点云处理，就通过 `/cloud_registered_no_point_filter` 发布当前点云，其中可以同时包含静态物体和动态物体的点。

M-detector接收当前点云，识别其中的动态点，并将被判为静态的点保留下来。程序累积近期若干帧的静态点，形成静态背景点云，通过 `/m_detector/std_points` 发布。默认最多累积5帧；达到上限后，每加入一帧，就移除最旧的一帧。当前启用的聚类耦合分支还会进行体素降采样，将同一空间小格内的多个点合并为代表点，以减少数据量。

这些静态点使用世界坐标保存，因此无人机移动后，不同帧中观察到的同一面墙仍能在共同的坐标系中累积。例如，一根细杆当前帧没有被扫到，但前几帧观测到的静态点仍可能保留在背景中，从而补充当前扫描的缺失。



**第二步：规划节点将当前点云和静态背景点云转换到同一个局部规划坐标系。**

两份点云信息都减去当前参考时刻的无人机位置：

$$
Cₜ^{Pₜ}=Cₜ^{W}-pᵤₐᵥ^{W}(t),
$$

$$
Bₜ^{Pₜ}=Bₜ^{W}-pᵤₐᵥ^{W}(t).
$$



**第三步：分别生成当前点云距离图和静态背景距离图**

规划节点使用相同的96×360角度网格，分别投影两份点云，得到：

- 当前点云距离图 D_{current}；
- 静态背景距离图 D_{background}。

每张图内部都按同一规则处理：根据点的方位角和俯仰角确定格子，同一格有多个有效点时保留最近距离；没有有效点的格子暂填默认最大距离20米。

因为两张图采用相同的规划坐标系和角度网格，**相同行、相同列对应同一个观察方向，可以逐格比较。**



**第四步：逐格保留较近的距离**

程序对两张距离图执行：

```
base_range = np.minimum(current_range, static_range)
```

即：
$$
D_{base}(h,w) = min( D_{current}(h,w), D_{background}(h,w) ).
$$
5.如何合成**可见动态目标球体的表面距离**

**第一步：根据跟踪结果确定球体。**

对于每个已确认的动态目标，程序取出其位置和尺寸。目标位置经过时间对齐后，转换到与基础距离图相同的局部规划坐标系，作为球心 c。

球体半径取目标三个尺寸中最大值的一半，再限制在配置范围内：
$$
R=clip ( max(dₓ,d_{y},d_{z})/2, Rₘᵢₙ,Rₘₐₓ ).
$$
当前默认范围为：Rₘᵢₙ=0.10米,  Rₘₐₓ=0.20米.

例如，目标尺寸为 (0.3,0.3,0.4) 米，得到半径0.2米。

**这个球体是根据跟踪结果构造的近似模型，不是真实表面的精确重建。** 半径还有上限，因此也不能保证完整包住任意尺寸的目标。

**第二步：计算网格方向是否与球体相交。**

前面定义的96×360角度网格中，每个格子都对应一个观察方向。程序将这个方向表示为从无人机位置出发的单位射线：
$$
p(s)=sd,  s>0,
$$
其中 d 是该方向的单位向量，s 就是沿射线的距离。

球体表面满足：
$$
‖p-c‖²=R².
$$
将射线代入，得到：
$$
‖sd-c‖²=R².
$$
求解这个方程，就能判断射线有没有碰到球体，以及碰到表面时的距离。对于无人机位于球体外部的通常情况，保留最近的有效交点：
$$
sₙₑₐᵣ = d^{⊤}c - √( (d^{⊤}c)²-‖c‖²+R² ).
$$
根号内小于零，表示这个方向没有碰到球体。

例如，沿正对球心的方向观察，球心距离4米、半径0.2米，那么最近表面距离就是：4-0.2=3.8米.旁边稍偏一些的方向可能也与球体相交，但表面距离通常不同。这样，球体会在全景图上覆盖一片区域。

**第三步：多个动态目标覆盖同一格时，先保留最近的动态表面。**

假设某个方向同时穿过两个动态目标，表面距离分别为3.8米和6米，程序先保留3.8米，以及对应目标的速度信息。

为减少计算，当前实现会先估计每个球体可能覆盖的角度区域，通常只对这个区域中的射线求交。

**第四步：与基础距离图比较，判断是否被遮挡。**

射线与球体相交，并不意味着该目标应该显示出来：前面可能还有墙或其他更近的表面。

当前默认的可见性判断为：
$$
D_{dynamic}<20米,
$$
并且：
$$
D_{dynamic} ≤ D_{base}+0.15米.
$$
这里的0.15米是遮挡容差，用于容纳点云与球体模型之间的小误差。

**第五步：可见位置取较近距离，其他位置保持原值。**

对于判为可见的格子：
$$
D_{new}(h,w) = min( D_{base}(h,w), D_{dynamic}(h,w) ).
$$
例如，基础距离为6米、球体表面为3.8米，就更新为3.8米；基础距离为3.7米、球体表面为3.8米，即使通过了容差判断，距离仍保留3.7米。





#### 动态掩码图构建：

在当前点云与静态背景融合得到基础距离图后，规划节点利用 M-detector 发布的已确认动态目标，构建与距离图空间对齐的动态掩码。动态目标来自 `/m_detector/confirmed_tracks`，每个目标包含跟踪位置、尺寸和三维速度。规划节点先把目标状态外推到当前感知参考时刻，并转换到与距离图一致的规划坐标系。随后，当前代码用一个球体近似目标：球心取跟踪位置，半径由目标尺寸计算，并限制在配置范围内。这样，即使雷达只在目标上收到少量回波，程序也可以根据跟踪得到的几何模型，在角度网格中建立较完整的目标投影区域，而不只是标记零散的动态点。

具体生成投影时，96×360 网格中的每个位置都对应一条从无人机出发的单位方向射线。程序计算这条射线是否与目标球体相交；如果相交，就得到沿该方向到目标表面的距离。随后，把这个距离与基础距离图中的场景距离比较，判断目标是否可见。例如，该方向上球体表面位于 4 米处，而场景中最近的墙在 6 米处，目标可以被标记为可见；如果墙在 2 米处，球体位于墙后，就不应在该位置写入动态目标信息。代码在比较时保留一定的遮挡容差，以适应点云和跟踪模型之间的误差。多个动态目标覆盖同一方向时，优先保留较近的动态表面，再进行可见性判断。

程序将动态表面距离与**补全前的基础距离图**比较，判断该方向上的动态目标是否被更近的表面遮挡。当前默认条件为：
$$
D_{dynamic}(h,w)<20米,且：

D_{dynamic}(h,w) ≤ D_{base}(h,w)+0.15米.
$$
通过上述判断，程序得到动态掩码 M：属于可见动态目标投影的位置为 1，其他位置为 0。**掩码表达的是“这个方向是否被当前确认的动态目标占据”，并不表达目标速度，也不是碰撞概率。** 同一个目标通常覆盖多个相邻格子，形成一个二维区域。还需要注意，M=0 只表示该位置没有被当前动态感知链标记为动态，可能对应静态物体、空白方向、被遮挡目标或漏检区域，不能一概理解为“这里一定静止或安全”。动态球体模型也会参与距离图的合成，因此动态目标区域的距离、掩码和速度共同描述同一个目标表面。



#### 速度图构建：

速度图与动态掩码在同一次球体投影和遮挡判断过程中生成。速度图是在这个可见动态区域上进一步填写运动信息。对于目标覆盖的每个格子，程序将该目标在规划坐标系中的速度 (vₓ,v_{y},v_{z}) 分别写入 Vₓ、V_{y}、V_{z} 三张图；多个动态目标覆盖同一格时，使用前面选出的最近动态表面所对应目标的速度；没有被动态掩码标记的位置，速度设为零。例如，一个球以 (-2,1,0) m/s 运动，它在全景图上覆盖了 20 个格子，那么这些格子的三维速度都填为 (-2,1,0)。因此，速度图虽然具有逐像素形式，当前实现填入的主要是**目标级平移速度**，并没有估计球体每个表面点因自转产生的不同速度。它也不是本机与目标的相对速度；本机速度通过另一条状态输入提供给网络，由网络结合两者判断相对运动。



#### 五通道对齐与距离补全：

完成距离图、动态掩码和速度图的构建后，同一个网格位置就对应五个数：距离、动态标记以及三个方向的速度。**五通道就是五张共享角度网格的二维图，相同行、相同列表示同一个观察方向。** 距离图表达场景几何，动态掩码标记可见动态目标的模型投影，速度图记录对应目标的三维平移速度。

例如，在距离归一化之前，某个格子记录 `[4,1,-2,1,0]`，表示该方向的距离值约为4米，该格被标记为动态，对应目标的速度为 (-2,1,0) m/s。这里的对齐表示五个数关联于同一个网格方向；由于目标使用球体近似，且遮挡判断允许一定容差，距离值与动态标记、速度不一定严格对应同一个真实表面点。

雷达观测较稀疏，当前点云中没有回波的格子，可以先由静态背景或动态目标球体模型补充距离。完成这些融合后，程序再对仍然缺失的距离进行补全：利用水平和垂直方向已有的距离进行插值，并对补全位置做小范围平滑，原有有效距离保持不变。动态掩码和速度图不进行同样的空间扩散，以免把动态标记和运动信息传播到目标投影之外。



#### 尺寸映射与张量组装

接下来，程序将这套数据从 **96×360 映射到网络规定的 96×384**。项目设计了 3 个垂直方向、12 个水平方向，共 36 个候选，而编码器会将输入高宽各缩小 32 倍，因此输入尺寸选择为 96=3×32、384=12×32，使输出特征网格恰好为 3×12。前端使用 360 列，则便于采用水平方向 1° 一列的投影约定。两套尺寸之间通过列索引转换：新图第 j 列取原图第 ⌊ j×360/384⌋ 列， j=0,…,383，对地取整。这会均匀重复部分原始列，没有补零，也没有增加真实测量信息。距离、掩码和速度使用完全相同的列映射，保证它们继续对齐。直接将点云投影到 384 列理论上也是可行的，360→384 是作者的实现选择，是否最优同样有待商榷。

经过尺寸映射和距离归一化，论文所说的统一输入可以写成 I=[D,M,V]，形状为 **96×384×5**。这里前两个维度是角度网格的高和宽，最后一个维度表示每个方向记录五个数。转换成 PyTorch 的“批量×通道×高×宽”顺序后，单帧完整表示相当于 `[1,5,96,384]`。但实际代码保留三个独立参数：距离为 `[1,1,96,384]`，动态掩码为 `[1,1,96,384]`，速度图为 `[1,3,96,384]`。所谓“统一”，主要指这些数据共享角度网格、坐标系和参考时刻，而不是必须先拼成一个变量才能输入网络。



#### 双分支编码与状态输入

进入双分支网络后，距离图 `[B,1,96,384]`单独送入距离编码器，掩码和速度图沿通道轴拼成四通道输入 `[B,4,96,384]`，送入动态编码器。两个编码器结构相近，但使用各自独立的网络参数，分别提取场景几何特征和动态运动特征。

两个编码器均使用修改后的ResNet-18，当前实现跳过最大池化，通过首层卷积和四个残差阶段的下采样依次进行2倍下采样

| 处理阶段       | 输出形状        |
| -------------- | --------------- |
| 首层卷积       | `[B,64,48,192]` |
| 第一个残差阶段 | `[B,64,24,96]`  |
| 第二个残差阶段 | `[B,128,12,48]` |
| 第三个残差阶段 | `[B,256,6,24]`  |
| 第四个残差阶段 | `[B,512,3,12]`  |
| 最后1×1卷积    | `[B,64,3,12]`   |

因此，两路最终各得到一张3×12的特征网格，每个位置包含64个学习得到的特征值，与36个候选的位置对应。它们已经是网络内部特征，不再分别具有距离、掩码或速度的直接物理含义。在线处理单帧时，B=1。

为保持水平360°的连续性，编码器卷积采用环形填充：处理全景图左边界时可以使用右边界的数据，反之亦然。论文强调的是水平方向的循环连接；当前代码还对高度方向进行了环形填充，但俯仰角上下边界并不具有相同的循环关系。

网络还接收独立的9维状态输入，包括本机三维速度、三维加速度和相对目标向量。
$$
s= [v₀,a₀,gᵣₑₗ].
$$
其中，相对目标向量是导航目标位置减去感知参考时刻的无人机位置。三组向量先统一表达在局部规划坐标系中。当前雷达输入路径使用时间对齐后的里程计速度，并通过邻近里程计速度的差分估计加速度；无法获得满足时间条件的差分数据时，加速度设为零。

随后，程序进行尺度归一化：
$$
\[ \widetilde{\mathbf v}_0=\frac{\mathbf v_0}{v_s}, \qquad \widetilde{\mathbf a}_0=\frac{\mathbf a_0}{a_s}, \qquad \widetilde{\mathbf g} = \frac{\mathbf g_{\mathrm{rel}}} {\max(\|\mathbf g_{\mathrm{rel}}\|_2,L_g)}. \]
$$
这里，vₛ、aₛ、L_{g} 为配置中的速度、加速度和目标距离尺度。目标较远时，归一化后的目标向量主要保留方向；目标距离小于 L_{g} 时，其模长小于1，还保留接近目标的信息。速度和加速度只是除以尺度，没有额外裁剪，因此不能保证各分量始终位于 [-1,1]。

对于36个候选，每个候选都具有一个由其固定锚点方向确定的坐标系，称为**基元坐标系**，其中 x 轴沿该候选的锚点方向。程序将归一化后的速度、加速度和相对目标向量分别旋转到每个候选的基元坐标系，再按与候选输出一致的顺序排列，得到 `[B,9,3,12]` 的状态特征。

因此，这36个位置表达的是**同一份本机状态和目标信息在不同候选方向下的表示**。例如，同一个目标对某个候选可能位于前方，对另一个候选则可能位于侧方，有助于网络评价不同候选与当前运动及导航目标的关系。当前状态分支没有额外的可训练编码层，主要通过归一化、坐标旋转和排列形成状态特征，并提供给后续两个预测头。



**为什么将距离图与掩码、速度图分开编码？**

因为它们承担的任务不同：

| 输入             | 提供的信息                         | 主要用途                     |
| ---------------- | ---------------------------------- | ---------------------------- |
| 距离图           | 各方向表面离无人机多远             | 判断可通行空间，生成候选轨迹 |
| 动态掩码＋速度图 | 哪些区域属于动态目标，目标怎样运动 | 评价候选轨迹的动态风险       |

距离图主要描述几何形状，速度图则包含有正负方向的运动数值。使用两个具有独立参数的编码器，可以分别学习适合这些数据的特征。

但两路并不是完全分开使用：**静态头使用距离特征和状态特征；动态头同时使用距离特征、动态特征和状态特征。** 动态风险既取决于目标速度，也取决于目标距离和无人机运动，只有速度信息不够。

这种分支设计还实现了论文强调的“候选生成与动态评价分离”：固定距离图、状态和网络权重时，单独改变掩码或速度图，只会影响动态评分，不会直接改变候选终端状态。论文将这一设计用于抑制运动估计波动引起的轨迹抖动。这里仍需注意，距离图也包含动态目标几何，所以目标位置变化仍可能改变候选形状。

**2．为什么编码器采用修改后的ResNet-18，并逐步下采样？**

首先，距离图、掩码和速度图都已经排列成二维角度网格。相邻格子对应相近的观察方向，一个障碍物通常覆盖一片相邻区域，因此适合用卷积提取局部结构，再逐层结合更大范围的信息。

逐步下采样有两个作用：

- **扩大每个特征位置能够利用的观察范围**，让网络结合周围障碍物判断某个方向是否适合通行。
- **压缩空间尺寸和计算量**，将96×384的输入整理为3×12的候选特征网格。

残差结构允许每个模块在已有特征基础上学习修正，有助于训练较深的网络。水平方向的环形填充，则让全景图左右边界能像普通相邻区域一样交换信息。

最终的3×12对应36个候选，每个位置的64个特征值用于后续预测。**这些特征是学习得到的表示，不能理解为64个障碍物或64种预先规定的物理量。**

这里的结构属于工程设计选择：ResNet-18提供一定的特征提取能力，32倍下采样与3×12候选网格共同确定输入尺寸。论文没有证明18层、64通道或这套下采样安排是最优组合。



**．为什么五通道输入之外，还需要本机速度？**

因为速度图填的是**目标速度**，没有包含本机速度。

例如，同一张距离图显示前方4米有一堵墙，动态掩码和速度图都为零。此时：

- 无人机正在悬停，可以继续保持或缓慢接近；
- 无人机正以6 m/s朝墙飞行，就需要更早减速或转向。

两种情况下五通道图可以完全相同，但合理的轨迹明显不同。**仅凭单帧图像，网络无法确定无人机自身的运动状态。**

即使动态目标速度已知，也需要结合本机速度判断相对运动。目标以2 m/s向某方向运动，与无人机静止、同向追赶或迎面飞行，对应的风险都不同。



**为什么还需要本机加速度？**

因为当前速度相同，也不代表运动状态相同。

例如，两架无人机都以3 m/s向前飞，一架正在加速，另一架正在减速。后续轨迹若要与当前运动平顺衔接，所需的终端状态和轨迹形状会不同。

本项目重建五次多项式轨迹时，需要起点的位置、速度和加速度作为边界条件。因此，向网络提供加速度，可以帮助它生成与起始运动状态更协调的候选。

这里输入的是前面核实过的**里程计速度差分估计的加速度**，不是直接输入IMU原始读数。



**为什么需要相对目标向量，而且要单独输入？**

距离图描述周围环境，却没有告诉网络导航目标在哪里。同一处路口，向左走和向右走都可能安全，但只有一个方向更接近当前目标。

相对目标向量：
$$
gᵣₑₗ = p_{goal}-pᵤₐᵥ
$$
提供目标相对于无人机的方向和距离信息。它与三维速度、三维加速度合起来，正好形成：3+3+3=9维.

当前局部规划原点已经设在无人机位置，因此无需再用三个数重复输入本机在局部系中的位置——它始终为零。

这些状态原本就是少量向量，直接归一化并转换到各候选坐标系，便能清楚地提供给预测头，没有必要先编码成全景图。转换后，同一运动或目标向量在不同候选方向下具有不同分量，使网络更容易判断：**这个候选是否顺着当前运动、是否朝向目标，以及是否可能与动态目标相遇。**



### 网络输出：36组终端状态参数 + 36个静态评分 + 36个动态评分



#### 预测头与候选评价

 静态头将64通道距离特征与9通道状态特征拼接，形成 `[B,73,3,12]`，再通过通道数为 `73→256→256→10` 的三层1×1卷积。每个网格位置输出10个数：前9个经 `tanh` 约束，作为终端状态参数；第10个经 `softplus` 转换为非负静态评分。终端位置部分需要进一步解码为相对锚点的角度偏移和半径，终端速度、加速度也需要缩放和坐标变换，才能得到物理意义上的 (p_{f},v_{f},a_{f})。静态评分学习的是包含静态安全、平滑、加速度和目标进展的综合代价，并非单纯评价离障碍物有多远。

动态头将64通道距离特征、64通道动态特征和9通道状态特征拼接成 `[B,137,3,12]`，再通过 `137→256→256→1` 的三层1×1卷积，输出 `[B,1,3,12]`，经 `softplus` 去掉单通道轴后输出 `[B,3,12]` 的36个非负动态评分。它同时使用几何和运动特征，是因为评价未来相遇不仅需要知道目标怎样运动，也需要结合目标距离、本机状态和候选方向。**动态头没有显式接收静态头输出的终端状态，也不在在线阶段重新沿候选轨迹计算解析风险。** 训练时，系统根据当前预测的候选轨迹计算解析动态代价，以 `log1p` 压缩后的结果作为对应候选的监督标签，让动态头学习快速近似这一评价过程。

最终，静态头负责根据距离和状态目标生成36条候选的终端边界，动态头负责对这些候选提供运动风险评价。固定网络权重、距离图和状态目标时，只改变动态掩码或速度图，会改变动态评分，但不会直接改变静态头的终端状态输出；不过距离图本身也包含动态目标的几何表面，因此目标位置变化仍可能通过距离图影响候选形状。在线系统将静态评分与加权动态评分融合，再结合连续性代价和切换滞回选出一个候选，随后才闭式重建所选轨迹。这样，五通道输入最终发挥的作用就清楚了：**距离提供几何基础，掩码定位动态区域，速度提供运动信息，双分支网络把它们转换成候选轨迹及其评价。**



其中，每组候选的终端状态由 **9个归一化参数**表示。它们经过 `tanh` 后输出，理论取值均在 (-1,1) 内，工程上通常记为 [-1,1]。**前3个参数描述终点的方向与距离，后6个描述终端速度和加速度，并不是直接输出9个具有物理单位的坐标值。**

第 i 个候选的输出可以写成：
$$
zᵢ= [z_{θ},z_{ϕ},zᵣ,  z_{vₓ},z_{v_{y}},z_{v_{z}},  z_{aₓ},z_{a_{y}},z_{a_{z}}]
$$

| 参数                       | 实际含义                         | 解码方式                |
| -------------------------- | -------------------------------- | ----------------------- |
| z_{θ}                      | 相对候选锚点的方位角偏移         | Δθ=z_{θ}×15^{∘}         |
| z_{ϕ}                      | 相对候选锚点的俯仰角偏移         | Δϕ=z_{ϕ}×10^{∘}         |
| zᵣ                         | 从规划原点到终点的径向距离参数   | r=(zᵣ+1)R               |
| z_{vₓ},z_{v_{y}},z_{v_{z}} | 候选基元坐标系中的终端速度参数   | 各分量乘以速度尺度 vₛ   |
| z_{aₓ},z_{a_{y}},z_{a_{z}} | 候选基元坐标系中的终端加速度参数 | 各分量乘以加速度尺度 aₛ |

这里的角度范围来自当前配置：水平方向允许在锚点左右各偏移15°，垂直方向允许上下各偏移10°。每个候选拥有固定的锚点方位角 θᵢ 和俯仰角 ϕᵢ，实际终点方向为：
$$
θ_{f}=θᵢ+Δθ,  ϕ_{f}=ϕᵢ+Δϕ
$$
随后将球面形式转换成规划坐标系中的终端位置：
$$
\[ \mathbf p_f= r\begin{bmatrix} \cos\phi_f\cos\theta_f\\ \cos\phi_f\sin\theta_f\\ \sin\phi_f \end{bmatrix} \]
$$
因此，网络通过调整角度偏移和半径，让候选终点在对应方向附近移动。当前训练配置中 \(R=\texttt{radio\_range}=5\) 米，所以径向距离范围约为 **0～10米**；在线巡航和避障配置中 R=4 米，对应约 **0～8米**。注意，`radio_range`在这段解码里是半径缩放参数，最大输出距离是它的两倍。

后6个参数先在候选自身的基元坐标系中缩放：
$$
v_{f}⁽ⁱ⁾ =vₛ[z_{vₓ},z_{v_{y}},z_{v_{z}}]^{⊤}
$$

$$
a_{f}⁽ⁱ⁾ =aₛ[z_{aₓ},z_{a_{y}},z_{a_{z}}]^{⊤}
$$



例如，某候选输出：

zᵢ= [0.2,-0.3,0, 0.5,0,0, 0,0,0]

按训练配置解码后，表示终点相对锚点方位偏移 +3^{∘}、俯仰偏移 -3^{∘}，终点距离为5米，基元系终端速度为 (3,0,0) m/s，终端加速度为零。再结合该候选的锚点方向，便能得到规划坐标系中的具体终端状态。

最终解码结果才是常用的九维物理状态：
$$
x_{f}= [p_{f,x},p_{f,y},p_{f,z},  v_{f,x},v_{f,y},v_{f,z},  a_{f,x},a_{f,y},a_{f,z}]
$$


### 网络训练过程：

训练在仿真环境中进行。仿真器除了生成全景距离图，还提供静态地图、动态物体身份、位置、尺寸和速度等真值。数据加载器利用这些信息构造距离、动态掩码和速度图，并准备本机速度、加速度及相对目标。与实机部署不同，训练时动态物体身份和速度主要来自仿真真值；为模拟真实检测中的不可靠性，程序对动态掩码加入一定的误检、漏检扰动。静态地图和动态目标真值还承担另一项职责：为网络当前生成的候选轨迹计算解析代价。**这些额外真值用于构造训练监督，不作为规划网络的额外输入。**

每个训练批次首先执行一次完整的网络前向计算。距离图经过距离编码器，动态掩码与速度图经过动态编码器，两类特征与状态目标特征送入预测头，得到36组候选终端状态、36个静态评分和36个动态评分。程序将终端状态参数解码成物理意义上的终端位置、速度和加速度，再结合起始状态，构建对应的五次多项式候选轨迹。**训练监督针对的是网络当前生成的轨迹，因此候选轨迹以及对应代价会随参数更新而变化，并非事先准备一套固定轨迹标签供网络模仿。**

终端状态的训练通过直接最小化轨迹代价完成。程序利用静态距离场评价轨迹与障碍物之间的净空，同时计算轨迹平滑代价、加速度代价和锚点方向引导代价。锚点引导要求不同候选沿各自的方向展开，避免36个候选都集中到全局目标附近，丧失全向选择能力。这些代价通过可微计算连接到预测的终端状态，反向传播时推动网络生成静态安全、平滑且具有方向覆盖的候选。**终端状态损失不包含动态风险，动态目标的运动主要通过后续候选评分影响轨迹选择。**

静态评分头则学习预测每条候选的综合静态代价。它的监督目标由平滑代价、静态安全代价、加速度代价以及全局目标引导代价组成。这里需要区分两种引导：终端状态损失使用各候选自己的锚点方向，保持候选多样性；静态评分目标使用实际导航目标，帮助系统在这些候选中选择能够推进任务的方向。程序使用 Smooth L1 损失比较预测评分与解析代价，并对解析目标执行 `detach`，使评分回归学习逼近目标值，同时阻止梯度通过标签计算路径反向修改候选轨迹。

动态评分头的监督来自非对称动态风险场。程序沿每条候选轨迹采样未来时刻，按照恒速模型预测动态障碍位置，计算同一时刻无人机与障碍物的相对位置和相对速度，再评价各向异性高斯场及其接近方向门控，最后跨采样时刻、跨障碍物累加，得到每条候选的动态代价。该代价经过权重缩放和 `log1p` 压缩后，作为动态评分头的回归目标，同样使用 Smooth L1 损失并停止目标梯度。对数压缩用于减小极端危险样本与普通样本之间的数值差距，避免少量大代价样本主导训练。

整个训练包含三项损失：终端状态的轨迹代价、静态评分回归损失和动态评分回归损失。当前默认设置将三项等权相加，执行反向传播，并使用 AdamW 联合更新两个编码器和两个预测头。距离特征被两头共享，因此动态评分损失也会更新距离编码器；动态编码器则通过动态评分损失学习运动特征。**头之间的输入隔离并不等于训练参数完全隔离，编码器也不是预先提取特征后保持冻结。**

训练结束后，保存的是整套网络的参数，包括编码器和预测头。在线部署仍从距离图、掩码、速度图和状态目标开始执行前向计算，但不再查询训练用静态距离场，也不再沿所有候选逐点累加解析动态风险，而是直接使用网络预测的评分进行选择。这里便体现了论文所说的“蒸馏”：**训练阶段用解析代价监督网络，部署阶段用网络的快速预测近似这些代价计算。**



### 网络外部后处理：

网络完成前向计算后，输出36组终端状态参数、36个静态评分和36个动态评分。此时尚未确定最终执行哪条轨迹。规划节点首先按照候选网格与基元编号之间的对应关系，解码终端状态：将位置参数转换为相对锚点的方位角偏移、俯仰角偏移和半径，得到终端位置；将速度与加速度参数按当前运行配置缩放，并旋转到规划坐标系。随后，把这些状态转换到世界坐标系，其中终端位置还需要加上感知参考时刻的无人机位置，才能得到实际的世界系目标位置。

接着，规划节点融合每个候选的静态评分和动态评分：

$$
Sᵢ=S_{static,i}+λ S_{dynamic,i},   i=1,…,36
$$
其中，静态评分已经包含静态安全、平滑、加速度和目标进展等代价，在线阶段无需再重复添加这些解析项。动态评分是网络学习的、经过对数压缩的风险代理值，不能直接解释为碰撞概率。λ 用于调整动态评分对选择结果的影响，由当前运行模式配置决定。当前代码区分巡航、避障和悬停模式：巡航与避障可以使用不同的融合权重，悬停模式则不执行常规规划轨迹。

为了减少相近候选之间的频繁切换，系统在融合评分上增加端点连续性代价，并采用切换滞回。当前实现保留上一轮选择的候选编号，在新一帧中，以该编号对应的当前候选端点为参考，对距离它更远的其他端点增加归一化惩罚。这里比较的是**当前帧中不同候选的端点距离**，并非直接比较新端点与上一帧保存的世界系历史端点。切换滞回进一步要求新候选的评分比原候选低出一定幅度，才允许切换；否则继续保留原候选编号。这些机制主要在持续避障的选择过程中抑制方向抖动。

确定候选编号后，程序取出对应的世界系终端位置、速度和加速度，以重建时读取的最新里程计位置、速度，以及当前期望加速度作为起始边界。这里的终点仍对应感知参考时刻建立的世界系位置，而起点使用更新后的本机状态，从而衔接感知与推理期间已经发生的运动。对于每个坐标轴，程序构建一条五次多项式，例如：

$$
x(t)=a₀+a₁t+a₂t²+a₃t³+a₄t⁴+a₅t⁵,  0≤ t≤ T
$$
起始与终止时刻的位置、速度和加速度共提供六个边界条件，唯一确定该轴的六个系数。三个坐标轴分别求解后，得到完整三维轨迹。该过程通过闭式矩阵计算完成，不需要在线迭代优化；正常选轨路径也无需先展开全部36条完整多项式，选中候选后再重建执行轨迹。

由于感知、推理和控制异步运行，网络结果在成为活动轨迹之前，还需要通过时效与一致性检查。规划节点检查结果是否属于当前模式版本、是否比已提交结果更新，以及是否超过允许的数据年龄，避免过期推理结果覆盖当前轨迹。通过检查、完成重建且当前模式允许轨迹控制后，新轨迹才被安装为活动轨迹。



### 规划器输出：

从算法表示上看，规划器最终得到的是一条具有确定时间范围的三维参考轨迹：

$$
p(t)=[x(t),y(t),z(t)]^{⊤},  0≤ t≤ T
$$
三个坐标轴各有六个多项式系数，共18个系数；对位置多项式求导，还可以得到连续的参考速度、加速度和jerk，即加速度的变化率。因此，这条轨迹不仅说明无人机应该经过哪些位置，还规定各时刻应具有怎样的运动状态。它是网络预测、评分选择和边界条件重建共同形成的规划结果，不能直接等同于神经网络本身的输出。

从实际通信接口看，规划节点并不把18个系数直接发送给底层控制器，而是通过周期为0.02秒、即50 Hz的定时器，对当前活动轨迹进行采样。每次生成一个 `quadrotor_msgs/PositionCommand` 消息，包含参考位置、速度、加速度、jerk、偏航角和偏航角速度，以及时间戳和轨迹状态标记，默认发布到 `/so3_control/pos_cmd`。因此，**内部保存的是连续轨迹，向控制器发布的是随时间更新的轨迹参考状态。** 当前全向模式通常保持已有偏航参考，偏航角速度设为零，无需让机头始终朝向运动方向。

底层控制器接收这些参考状态，并结合无人机的实时估计状态，计算实际的姿态和推力控制指令。当前实机路径可使用 `px4ctrl`，通过MAVROS向PX4发送控制指令；默认仿真路径则由 `NetworkControl` 驱动刚体动力学模型。因此，规划器输出的 `PositionCommand` 属于运动参考，还不是电机转速或最终执行器指令。轨迹采样与发布过程见 control_pub (OmniRisk/omnirisk_node.py:1896)。

规划与参考指令发布采用异步机制。在有效期内，即使某一轮推理尚未完成，定时器也可以继续采样上一条已提交轨迹；新轨迹安装后，再切换到新参考。发布前，程序还会检查轨迹是否超出时域、是否长时间未刷新，以及模式版本是否一致。轨迹失效时，系统在具备有效状态的条件下转为当前位置悬停参考，避免继续使用过期轨迹。这里的50 Hz是参考消息发布频率，不能直接视为神经网络推理频率或底层飞控的控制频率。
