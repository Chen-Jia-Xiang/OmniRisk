# 实机仿真复现流程

## 1.作者github仓库提供的实际部署流程

~~~
# In every terminal
source ros_ws/devel/setup.bash

# T1 MAVROS
sudo chmod 666 /dev/ttyACM0
roslaunch mavros px4.launch fcu_url:=/dev/ttyACM0:57600

# After MAVROS connects: IMU / attitude at 200Hz
rosrun mavros mavcmd long 511 105 5000 0 0 0 0 0  # HIGHRES_IMU
rosrun mavros mavcmd long 511 31  5000 0 0 0 0 0  # ATTITUDE_QUATERNION
rosrun mavros mavcmd long 511 83  5000 0 0 0 0 0  # ATTITUDE_TARGET

# T2 MID360 + FAST-LIO + EKF
roslaunch fast_lio fastlio_ekf.launch

# T3 px4ctrl
roslaunch px4ctrl run_ctrl.launch

# T4 M-detector
roslaunch m_detector detector_mid360.launch

# T5 OmniRisk
source omnirisk_env/bin/activate
cd OmniRisk && python omnirisk_node.py --use_tensorrt 1

# T6 RViz
rviz -d OmniRisk/omnirisk.rviz

# T7 Joystick goal (_input_mode:=usb | mavros)
cd OmniRisk && python3 rc_goal_teleop.py _input_mode:=usb

# Takeoff / land
rostopic pub -1 /px4ctrl/takeoff_land quadrotor_msgs/TakeoffLand "takeoff_land_cmd: 1"
rostopic pub -1 /px4ctrl/takeoff_land quadrotor_msgs/TakeoffLand "takeoff_land_cmd: 2"

# Checks
rostopic hz /ekf_quat/ekf_odom              # > 50Hz
rostopic hz /mavros/setpoint_raw/attitude   # > 100Hz
rostopic hz /so3_control/pos_cmd
~~~



## 2.模块之间的通信

各个模块之间通过ROS话题通信

| 模块                       | 建议运行位置   | 作用                                     |
| -------------------------- | -------------- | ---------------------------------------- |
| T1 MAVROS                  | 机载电脑       | 通过 USB/串口连接 PX4 飞控               |
| T2 MID360 + FAST-LIO + EKF | 机载电脑       | 接收雷达数据，估计无人机位置、速度和姿态 |
| T3 px4ctrl                 | 机载电脑       | 将规划指令转换为飞控接收的姿态、推力指令 |
| T4 M-detector              | 机载电脑       | 检测和跟踪动态障碍物                     |
| T5 OmniRisk                | 机载电脑       | 加载模型，实时规划避障轨迹               |
| T6 RViz                    | 通常放地面电脑 | 显示点云、轨迹、状态                     |
| T7 Joystick goal           | 取决于输入来源 | 将摇杆操作转换为导航目标                 |



整体的数据流向为：

MID360 + FAST-LIO + EKF提供的周围静态障碍物点云信息以及无人机自身的位置速度姿态信息——>

M-detector根据点云信息检测并跟踪动态障碍物——>

Omnirisk接收depth+mask+velocity+obs四个张量输入神经网络，输出运动轨迹——>

px4ctrl根据期望轨迹、当前位姿、IMU 等信息计算期望姿态和推力，实现轨迹跟踪控制——>

MAVROS将轨迹跟踪信息转换为MAVLink信息，通过串口发送给PX4飞控执行。

## 3.各个模块的输入输出

### MID360雷达：测量环境并输出ROS数据

roslaunch fast_lio fastlio_ekf.launch中，会一起启动雷达驱动、FAT-LIO以及EKF



输入（或者也可以认为不需要输入）：

- MID360 通过网络发送的雷达测量数据。
- 雷达内置 IMU 的加速度计、陀螺仪数据。



输出：

| 话题topic      | 内容                                 |
| -------------- | ------------------------------------ |
| `/livox/lidar` | 雷达点云，FAST-LIO 接收的 Livox 数据 |
| `/livox/imu`   | 雷达自身 IMU 的测量                  |



该模块主要负责**负责采集和发布数据**



###  **FAST-LIO**：**通过雷达和 IMU 估计飞机运动**

要处理的问题：飞机相对于启动时建立的参考坐标系，移动了多少、转动了多少？



输入：

| 输入                    | 来源                                   |
| ----------------------- | -------------------------------------- |
| 雷达点云 `/livox/lidar` | 雷达驱动                               |
| IMU `/livox/imu`        | 雷达内置 IMU                           |
| 雷达与 IMU 的外参       | 配置文件，描述两者的相对安装位置和方向 |



输出：**输出：**

| 话题                                | 内容                     |
| ----------------------------------- | ------------------------ |
| `/Odometry`                         | 估计的位置、姿态、速度等 |
| `/cloud_registered_no_point_filter` | 转到世界坐标系的当前点云 |



核心过程：

**第一步：用 IMU 预测运动。**

​		 由上一时刻的位置、速度和姿态，利用角速度、加速度预测下一时刻状态。但 IMU 有噪声和偏置，积分时间越长，位置误差越容易累积。

**第二步：补偿扫描期间的运动畸变。**

​        一帧雷达数据中的点不是完全同时采集的。如果飞机在扫描期间移动，直接把所有点当作同一时刻的测量，会把墙面等结构“拉歪”。

FAST-LIO 利用 IMU 预测的运动，将这些点补偿到统一参考时刻。

**第三步：把当前扫描与已有局部地图匹配。**

​        根据已有局部地图，结合当前雷达扫描结果，修正飞机位姿

**第四步：迭代更新状态并维护地图**

​        通过迭代误差状态滤波，将 IMU 预测和雷达几何约束结合，更新位置、姿态、速度、偏置等状态，再把合适的点加入地图。

相关实现见 laserMapping.cpp (ros_ws/src/FAST_LIO/src/laserMapping.cpp:797)。

这里建立的“世界坐标系”通常是启动时定义的局部参考系，不必是 GPS 全球坐标系



### **EKF：将 FAST-LIO 状态与飞控 IMU 融合，提供高频状态**

**FAST-LIO 已经融合过雷达自己的 IMU，而这个额外 EKF 接入的是飞控通过 MAVROS 发来的 IMU**

主要作用：在雷达定位更新之间，持续提供适合控制使用的高频状态。



**输入：**

| 话题               | 内容                |
| ------------------ | ------------------- |
| `/Odometry`        | FAST-LIO 的位姿估计 |
| `/mavros/imu/data` | 飞控 IMU 数据       |



**输出：**

```
/ekf_quat/ekf_odom，
消息类型为 nav_msgs/Odometry，包含位置、姿态、速度等。发布频率与有效 IMU 输入及运行情况有关，不能仅凭配置保证一定达到 200 Hz。
```



当前实现维护的状态可以写成：

x=[p,q,v,b_{g},bₐ]

分别是位置、四元数姿态、速度、陀螺仪偏置和加速度计偏置。



**原理分为预测和校正：**

- 每来一条飞控 IMU，预测状态如何变化。
- FAST-LIO 位姿到达后，计算它与预测状态之间的误差。
- 根据状态和测量的不确定性，计算卡尔曼增益，修正状态。

由于 FAST-LIO 结果可能存在处理延迟，代码还保存历史状态和 IMU，用于在相应时间修正后，再向当前时刻重新传播。

因此，它不是把同一个低频位置复制很多次，而是在两次定位更新之间，利用真实 IMU 测量推进运动状态。

输入输出配置见 ekf_quat_lidar_mavros.launch (ros_ws/src/ekf_quat_pose/launch/ekf_quat_lidar_mavros.launch:3)。



###  **M-detector：判断哪些点属于运动物体，并跟踪它们**

FAST-LIO 回答“我在哪里”，M-detector 回答：环境中哪些东西正在动？它们在哪里，往哪里运动



输入是：

| 话题                                | 内容                           |
| ----------------------------------- | ------------------------------ |
| `/cloud_registered_no_point_filter` | 世界坐标系中的当前点云         |
| `/Odometry`                         | 与点云配合使用的 FAST-LIO 位姿 |

注意，当前默认检测器使用 `/Odometry`，规划器和控制器主要使用 `/ekf_quat/ekf_odom`，两者并不完全相同。



**主要输出：**

| 话题                                             | 内容                                   |
| ------------------------------------------------ | -------------------------------------- |
| `/m_detector/std_points`                         | 被判定为静态的点云                     |
| `/m_detector/confirmed_tracks`                   | 已确认动态目标的位置、速度、尺寸和 ID  |
| `/m_detector/point_out`、`/m_detector/frame_out` | 动态点相关输出，供跟踪、显示或调试使用 |



该模块分为动态障碍物检测和目标跟踪两部分

**① 动态点检测：比较多帧几何关系。**

仅比较两个点的坐标变化不够，因为无人机自己也在动。

系统需要利用位姿，将不同时间的测量放到可比较的参考关系中，再结合历史深度图检查：

- 当前点与静态环境是否一致。
- 同一方向的深度变化能否由遮挡解释。
- 多个时刻的观测是否支持该点属于运动物体。

例如，飞机移动时，墙在雷达局部坐标系中的位置会变；但经过正确的自身运动补偿，墙应保持在固定世界位置。飞来的球则仍会表现出独立运动。

**② 聚类：把动态点组成目标。**

一颗球可能产生多个雷达点。系统按空间邻近关系将其聚成点簇，计算中心、尺寸和包围盒。

**③ 数据关联：判断这一帧的球是不是上一帧那颗球。**

跟踪器先预测已有目标的位置，再比较当前检测与预测是否匹配。当前实现包含卡尔曼滤波、关联门限和匈牙利匹配等机制。

**④ 状态估计和生命周期管理。**

匹配后更新位置、速度；短暂漏检时做有限时间预测；缺乏足够观测或长期丢失的轨迹不再保留。

运动模型可配置为：

​						p(t+Δ t)=p(t)+v(t)Δ t

或加入已知重力的抛体模型：

​                       p(t+Δ t)=p(t)+v(t)Δ t+1/2gΔ t²                     

当前实机配置启用了抛体模型，适合投掷物；仿真匀速球配置会关闭它。

最终每个目标消息主要包含：

```
ID、是否确认、是否本帧匹配、年龄、命中次数、位置、速度、尺寸
```

实现见 DynObjFilter.cpp (ros_ws/src/M-detector/src/DynObjFilter.cpp) 和 FrameTracker.cpp (ros_ws/src/M-detector/src/FrameTracker.cpp)。



### **OmniRisk：将感知信息转换成可执行的避障轨迹**

使用已经训练好的网络进行轨迹预测



**输入：**

| 输入                                         | 用途                       |
| -------------------------------------------- | -------------------------- |
| 当前点云 `/cloud_registered_no_point_filter` | 表示当前可见环境           |
| 静态点云 `/m_detector/std_points`            | 提供静态环境信息           |
| 动态目标 `/m_detector/confirmed_tracks`      | 提供障碍物位置、速度和尺寸 |
| 状态 `/ekf_quat/ekf_odom`                    | 确定飞机当前运动状态       |
| 目标 `/move_base_simple/goal`                | 指定希望飞往的位置         |
| 模型权重或 TensorRT 引擎                     | 提供学习后的预测能力       |



**输出：**

```
/so3_control/pos_cmd
```

消息类型为 `quadrotor_msgs/PositionCommand`，主要包含期望位置、速度、加速度、jerk（加速度的变化率）、偏航角等。

它不是直接输出电机转速。



主要实现流程如下：

**① 对齐时间和坐标系。**

点云、动态目标和状态有各自时间戳，必须尽量表达同一时刻的场景。

例如，球每秒移动 4 米，错用 0.1 秒前的位置，就会产生约 0.4 米误差。当前代码包含缓存、同步、有限预测和过期结果丢弃机制。

**② 构造网络输入。**

三维点先转到以飞机为中心的规划参考系，再投影成球面距离图：

r=√(x²+y²+z²)

θ=atan2(y,x),  ϕ=atan2(z,√(x²+y²))

水平角和垂直角决定图像位置，距离决定像素值。

当前配置先构造约 `96×360` 的全景表示，再映射到网络使用的 `96×384`。

动态目标经过几何投影，形成：

- 障碍物掩码：哪些像素属于动态目标。
- 速度图：这些像素对应目标的三维速度。

另外构造 9 维状态：

```
当前速度3维 + 参考加速度3维 + 目标偏移3维
```

这里的参考加速度在运行时主要来自规划参考，并不是直接把 IMU 原始加速度塞进网络。

**③ 网络生成候选终点和评分。**

当前配置包含：

```
12个水平方向 × 3个垂直方向 = 36个候选
```

每个候选输出：

```
终点位置、终点速度、终点加速度
静态综合代价评分
动态风险评分
```

静态分支使用距离图和状态；动态分支额外使用掩码和速度图。

**④ 综合评分，选择候选。**

基本形式为：

Jᵢ=J_{static,i}+λ J_{dynamic,i}

然后选择代价较低的候选。当前代码还加入连续性代价和切换迟滞，避免相邻时刻频繁左右切换。

这些评分是模型预测的代价，不等于严格的碰撞概率。

**⑤ 用五次多项式构造连续轨迹。**

每个坐标轴使用：

p(t)=c₀+c₁t+c₂t²+c₃t³+c₄t⁴+c₅t⁵

利用起点和终点的：

```
位置、速度、加速度
```

共六个约束求出六个系数。

这样既能得到位置，也能通过求导得到速度、加速度和 jerk。当前控制参考定时器周期为 `0.02 s`，即名义上约 50 Hz；新的感知结果到来后会重新规划。

实现见 omnirisk_node.py (OmniRisk/omnirisk_node.py:1341)、network.py (OmniRisk/policy/network.py:47) 和 poly_solver.py (OmniRisk/policy/poly_solver.py:4)。

TensorRT 作用于这里的网络前向计算，周围的数据同步、投影、轨迹生成等仍由其他代码执行。



### **px4ctrl：把轨迹参考变成姿态和推力**



**输入：**

| 话题                    | 内容                     |
| ----------------------- | ------------------------ |
| `/so3_control/pos_cmd`  | OmniRisk 给出的期望运动  |
| `/ekf_quat/ekf_odom`    | 实际位置、速度和姿态     |
| `/mavros/imu/data`      | 飞控 IMU 和姿态信息      |
| `/mavros/state`         | 飞控连接、解锁、模式状态 |
| `/mavros/rc/in`         | 遥控输入                 |
| `/mavros/battery`       | 电池状态                 |
| `/px4ctrl/takeoff_land` | 起降请求                 |



**主要输出：**

```
/mavros/setpoint_raw/attitude
```

当前实际发送的是：

```
期望姿态四元数 q_d
归一化推力指令
```



具体控制包含以下步骤。

**① 比较期望与实际运动。**

当前代码使用串级位置、速度反馈。忽略限幅时，可近似写为：

v_{cmd}=v_{d}+Kₚ(p_{d}-p)

a_{cmd}=a_{d}+Kᵥ(v_{cmd}-v)

位置误差修正速度目标，速度误差再修正加速度目标。实际代码会限制误差和倾角等，避免过大的控制输出。

**② 将期望加速度转换成推力方向。**

忽略空气阻力时：

F_{d}=m(a_{cmd}-g)

四旋翼主要沿机体竖直轴产生总推力，所以要向右加速，就需要适当倾斜，使推力具有向右的分量。

结合期望偏航角，就能确定期望姿态；推力大小则与总力需求有关。

当前默认算法还利用轨迹 jerk 等信息计算前馈量，并进行飞控姿态参考系对齐。

**③ 将力需求转换为实际推力指令。**

发给 PX4 的 `thrust` 是归一化指令，并不是牛顿值，也不是简单的“电机油门百分比等于推力百分比”。

控制器需要使用推力模型，将加速度需求映射为指令，并可根据 IMU 反馈估计模型参数。

**④ 状态机管理。**

px4ctrl 还管理手动、悬停、轨迹跟踪、起飞和降落等状态，并通过 MAVROS 请求解锁、切换 Offboard 模式。

当前配置最大控制循环频率为 200 Hz，实际频率仍需要运行测量。

一个关键细节：虽然代码中也计算了角速度相关量，**当前发布函数将角速度设为忽略，实际采用姿态加推力接口**，见 PX4CtrlFSM.cpp (ros_ws/src/px4ctrl/src/PX4CtrlFSM.cpp:567)。位置速度反馈实现见 controller.cpp (ros_ws/src/px4ctrl/src/controller.cpp:690)。



### **MAVROS：连接 ROS 与 PX4 的通信桥梁**

主要解决：ROS 程序中的消息，怎样变成 PX4 能理解的通信数据？飞控数据怎样返回 ROS？



它有两个方向。

**机载电脑 → 飞控：**

| ROS 输入                        | 发给飞控的内容   |
| ------------------------------- | ---------------- |
| `/mavros/setpoint_raw/attitude` | 姿态和推力设定值 |
| `/mavros/set_mode` 服务         | 模式切换请求     |
| `/mavros/cmd/arming` 服务       | 解锁、上锁请求   |

MAVROS 将这些转换为 MAVLink 消息，通过 USB、UART 或其他配置好的链路发送。

**飞控 → 机载电脑：**

| ROS 输出           | 内容                 |
| ------------------ | -------------------- |
| `/mavros/imu/data` | IMU 测量和姿态       |
| `/mavros/state`    | 连接、解锁、飞行模式 |
| `/mavros/rc/in`    | 遥控通道             |
| `/mavros/battery`  | 电池数据             |

MAVROS 还处理接口约定下的坐标转换。ROS 常使用 ENU、FLU，而 PX4 常使用 NED、FRD，不能把两套坐标中的数值未经转换直接互用。

它本身不负责选择避障路线，也不负责本项目中的轨迹跟踪控制律。



### **PX4：执行姿态和角速度控制，分配电机输出**

PX4 运行在飞控硬件中。

**输入：**

- MAVROS 传来的期望姿态和推力。
- 飞控本地 IMU、姿态估计。
- 遥控、模式和其他飞行状态。

**输出：**

- 各电机的执行指令，通过 PWM、DShot 等接口发送给电调。
- 经 MAVLink 返回的状态和传感器消息。

在这套“姿态＋推力”接口下，可以理解成：

```
期望姿态与实际姿态的误差
    ↓
生成期望角速度
    ↓
期望角速度与陀螺仪角速度的误差
    ↓
计算所需力矩
    ↓
结合总推力，进行控制分配
    ↓
各个电机指令
```
